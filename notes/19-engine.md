# Единый движок picPac One: как работает, требования, что есть и что сделать

Записано 11.11. Продолжение notes/07 (архитектура), notes/14 (бэкенд), notes/18 (советы преподавателя). Всё ниже — **рекомендация**, команда не подтверждала. Срок: отбор финалистов 12.11 в 17:45.

## 1. Идея в трёх фразах

1. **Один ИИ-движок, разные роли.** Клиент в приложении, менеджер и руководитель в рабочем месте (Insight) обращаются к одному движку. Модель одна, а набор разрешённых действий и данных у каждой роли свой.
2. **Общие данные.** Заказ из приложения, этапы производства, претензии, решения руководителя лежат в одной базе.
3. **Замкнутый контур качества.** Решение руководителя меняет пороги проверки фото в приложении, а система сама проверяет по данным, помогло ли оно.

```
 Приложение (клиент)        Сайт (клиент)        Insight: дашборд + ассистент (менеджер, руководитель)
        \                        |                        /
         \______________ один API (FastAPI) _____________/
                               |
        +----------------------+-----------------------+
        |                      |                       |
   Путь заказа            ИИ-движок              Insight
   фото, проекты,     права → выбор действия →   события, витрины,
   сборка, заказы     выполнение → ответ →       отклонения, решения,
                      журнал                     проверка эффекта
        |                      |                       |
        +----------- PostgreSQL (одна база) -----------+
                               |
              локальные модели: языковая (Ollama), лица и качество фото,
              поиск по документам, распознавание речи
```

## 2. Как движок обрабатывает один запрос

Один вход для всех ролей: `POST /assistant/ask` с текстом и токеном пользователя. Порядок шагов задан кодом, модель его не меняет.

| # | Шаг | Кто делает | Что происходит |
|---|---|---|---|
| 1 | Кто спрашивает | Код | Из токена берём пользователя и роль |
| 2 | Что ему доступно | Код | Собираем список действий только для этой роли. Действий других ролей в списке нет вообще |
| 3 | Проверка запроса | Код | Ограничение длины и частоты. Телефоны, почты, имена заменяются метками («клиент_17») |
| 4 | Выбор действия | Модель, 1-й вызов | Модель выбирает одно действие из списка и его параметры. Ответ жёстко ограничен схемой: выдумать действие или параметр нельзя. Вариант «не знаю / нет такого действия» в схеме есть |
| 5 | Выполнение | Код | Код выполняет действие с правами пользователя: запрос к витрине, поиск по документам, чтение своих заказов |
| 6 | Ответ | Модель, 2-й вызов | Модель пишет ответ по результату шага 5. Тексты из документов и от клиентов передаются как данные в отдельном блоке, команды внутри них не выполняются |
| 7 | Проверка ответа | Код | Все числа в ответе должны быть в результате шага 5, иначе ответ заменяется таблицей с цифрами. Метки возвращаются в имена только тем, у кого есть право |
| 8 | Журнал | Код | Кто, что спросил, какое действие, какие данные, что ответили. Каждая запись содержит отпечаток предыдущей |

**Запись в базу (решение, задача, изменение порога)** модель не делает никогда. Она возвращает предложение, человек подтверждает его отдельной кнопкой, и запись выполняет обычный API.

### Действия по ролям

| Действие | Клиент | Менеджер | Руководитель |
|---|---|---|---|
| Разобрать описание книги (Story Mode) | да | — | — |
| Статус своего заказа | да | — | — |
| Справочник: сроки, форматы, доставка | да | да | да |
| Претензия по браку | да | — | — |
| Метрика из каталога (заказы, брак, сроки) | — | да | да |
| Метрика из каталога (финансы, кадры) | — | — | да |
| Поиск по внутренним документам | — | по правам | да |
| Повестка встречи, протокол, предложение решения | — | — | да |

### Каталог метрик

Модель не пишет запросы к базе. Она выбирает из каталога метрику, разрез и период, а запрос строит код. Тот же каталог питает дашборд, поэтому цифра в чате и на графике всегда одна.

Запись каталога: название, единица, витрина, как считать, допустимые разрезы (продукт, линия, смена, день), каким ролям доступна, что считать ухудшением (рост или падение).

Минимум для демо: доля брака, выручка, маржа, срок изготовления, доля отказов в приложении.

## 3. Контур качества

| # | Шаг | Где |
|---|---|---|
| 1 | Клиент собирает книгу, сервер проверяет фото по текущим порогам (поле у края, разрешение, резкость) | Приложение, `ai/quality.py` |
| 2 | Заказ проходит этапы производства: линия, смена | `order_stages` |
| 3 | Клиент сообщает о браке, претензия привязана к заказу, линии и смене | Претензии |
| 4 | Раз в день считается доля брака по линиям и сменам. Норма — медиана за прошлые недели, отклонение — по устойчивому расчёту (notes/18, раздел 2) | Insight |
| 5 | Создаётся карточка отклонения. Раскладка по разрезам показывает, какой из них объясняет рост сильнее всего | Insight |
| 6 | Руководитель оформляет решение: причина, действие, ответственный, срок. Одно из возможных действий — изменить порог проверки фото | Insight |
| 7 | Порог сохраняется как новая версия политики качества. Следующая сборка книги в приложении проверяется уже по ней | Политика качества |
| 8 | Через заданный период система сравнивает медианы «до» и «после»: помогло — отклонение закрыто, нет — карточка открыта снова | Insight |

Пороги сейчас записаны константами в `ai/quality.py`. Их нужно вынести в таблицу с версиями, чтобы шаг 7 работал и чтобы было видно, какое решение какой порог изменило.

## 4. Требования

**Что система должна уметь (к демо):**
1. Клиент оформляет заказ в приложении, заказ появляется в базе и в Insight.
2. Insight показывает показатели, находит одно отклонение, раскладывает его до причины.
3. Руководитель задаёт вопрос ассистенту и получает ответ с цифрами из каталога и ссылкой на источник.
4. Руководитель оформляет решение, решение меняет порог, эффект проверяется.
5. Клиент или текст в документе не могут заставить ассистента выдать данные компании.
6. Всё работает без интернета.

**Как она должна работать:**
- **Скорость.** Цели из notes/07: ответ ассистента до ~10 с, автосборка книги из 40 фото до ~30 с. Обе не измерены. Отсюда ограничение: не больше двух вызовов модели на ответ.
- **Точность цифр.** Числа считает код. Критерий из UC-M1: все числа в ответе совпадают с витринами.
- **Права.** Проверяются кодом до модели (шаги 1–2), а не текстом инструкции для модели.
- **Запасной режим.** `DEMO_MODE` с заранее посчитанными ответами на вопросы демо-сценария, если модель тормозит.
- **Приватность фото.** По notes/17.

## 5. Ограничения

| Ограничение | Что из него следует |
|---|---|
| **Время:** до отбора около суток | Узкий сквозной срез, а не все сценарии. См. раздел 7 |
| **Железо:** MacBook Air M3, 16 ГБ, без вентилятора; на нём же база, API, веб | Одна языковая модель 7–8B в 4-битном виде. Запросы к модели идут по очереди, не параллельно. Распознавание речи и языковая модель одновременно в память могут не поместиться: аудио встречи расшифровываем заранее или загружаем текст |

## 7. Минимальный срез к отбору

Один сценарий, который проходит целиком:

1. В приложении оформляется заказ → он появляется в Insight.
2. В Insight видно отклонение по браку на одной линии (из тестовых данных).
3. Клик → причина: линия, смена.
4. Вопрос ассистенту «почему вырос брак?» → ответ с цифрами и источником.
5. Решение «увеличить поле у края» → порог меняется → новая книга в приложении получает предупреждение по новому порогу.
6. Проверка эффекта на тестовых данных «после».
7. Клиент пишет в приложении «покажи выручку компании» → отказ, запись в журнале.

Всё остальное из раздела 6 — после отбора или слайдом.

**Порядок работ.** Генератор данных и таблицы событий, претензий, отклонений можно делать параллельно с подключением модели. Веб-часть зависит от API Insight, поэтому формат ответов нужно согласовать первым.
