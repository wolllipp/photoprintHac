# Концепция: единая платформа на три трека

Название: **picPac One** (решение команды). Идея: одна система вместо трёх. Клиентская часть называется **picPac**, дашборд — **picPac Insight**, помощник — **picPac Ассистент**.
Идея: одна система, где данные идут от клиента к руководителю по одному контуру. Это прямо отвечает слову «объединят» из описания хакатона.

```
 [Трек 2: приложение]  -->  [Трек 1: данные и дашборд]  -->  [Трек 3: AI-помощник]
   заказы, события           очистка, метрики, причины         анализ, встречи, решения
        ^                                                              |
        +------------------- обратная связь (задачи, акции) -----------+
```

## 1. Приложение для клиентов (трек 2)
Цель: сократить путь «фото на телефоне -> оформленный заказ».

- Выбор фото из галереи, автоподбор продукта (печать, фотокнига, магнит, холст) по содержимому и числу фото.
- Автокадрирование и проверка качества: предупреждение о низком разрешении, обрезке лиц.
- Заказ в 3 шага: фото -> продукт (предпросмотр) -> доставка и оплата.
- Повтор прошлого заказа в один тап.
- Каждый шаг пишет событие в общий поток данных (откуда клиент ушёл, сколько занял путь).

Демо-метрика: количество тапов и секунд до заказа, до и после.

## 2. Данные и обработка (трек 1)
Цель: связать финансы, клиентов, производство, кадры и дойти от агрегата до причины.

- **Слой данных:** генератор обезличенных тестовых данных, загрузка (CSV/API), чистка, дедупликация, контроль качества (пропуски, выбросы, нарушения схемы).
- **Единая модель:** заказ связан с клиентом, производственной сменой, сотрудником и выручкой.
- **Дашборд:** KPI на верхнем уровне, drill-down «выручка упала -> какой продукт -> какой цех -> какая смена -> брак/нехватка людей».
- **Оформление решения по отклонению:** карточка отклонения (причина, ответственный, действие, срок, статус). Это ключевой глагол трека.
- Пайплайн с проверками качества данных виден в демо, а не спрятан.

## 3. AI-помощник руководителя (трек 3)
Цель: защищённый помощник, который работает поверх данных трека 1.

- **Анализ:** вопрос на естественном языке («почему упала маржа на фотокнигах?») -> запрос к данным -> объяснение с источниками.
- **Встречи:** повестка из текущих отклонений до встречи, запись/протокол во время, итоги, задачи и ответственные после.
- **Документы:** поиск по корпоративным документам (RAG) с проверкой прав доступа.
- **Задачи:** решения из карточек отклонений превращаются в задачи, статус возвращается в дашборд.
- **Защита (лекция 3 про это):**
  - ролевой доступ: помощник видит только то, что видит пользователь;
  - маскирование персональных данных до отправки в модель;
  - защита от prompt injection в документах;
  - журнал действий и ответов со ссылками на источник;
  - вариант с локальной или частной моделью для чувствительных данных.

## 4. Сквозной сценарий демо (главное для жюри)
1. Клиент оформляет заказ в приложении за N секунд.
2. Событие и заказ появляются в данных, дашборд обновляется.
3. На дашборде видно отклонение (например, рост отмен в одном цеху).
4. Руководитель спрашивает помощника: «что случилось?». Тот проводит от агрегата к причине.
5. Помощник готовит повестку встречи, после встречи создаёт решение и задачи.
6. Решение закрывает отклонение, цикл замкнут.

Одна история на 5 минут лучше трёх отдельных демо.

## 5. Архитектура (для «пути к промышленному развитию»)
- Клиент: мобильное приложение (кроссплатформенное, например React Native / Flutter) или PWA как запасной вариант.
- Бэкенд: один API-сервис, события в очередь/таблицу событий.
- Хранилище: PostgreSQL (операционные данные + аналитические представления).
- Слой AI: оркестратор с инструментами (SQL по разрешённым представлениям, поиск по документам), права проверяются до вызова модели.
- Слайд «от прототипа к продукту»: что заменяется (генератор -> реальные источники, SQLite -> кластер, и т.д.).

## 10. Принятые решения (после обсуждения)

### 10.1 Весь AI работает в локальном контуре
Данные компании и фото клиентов не уходят во внешние API. Это становится главным аргументом «защищённости» в треке 3.

- **LLM для помощника:** открытая модель, запущенная локально (Ollama / vLLM). Конкретную модель выбираем под доступное железо, это нужно проверить до 11.11.
- **Работа с фото:** локальные модели для эмбеддингов изображений, оценки качества, поиска лиц и дубликатов.
- **Речь на встречах:** локальное распознавание (например Whisper-класс моделей).
- **Поиск по документам:** локальная векторная база и локальные эмбеддинги.
- **Граница контура:** в демо показать схему «что внутри периметра» и доказать это (например, сеть отключена, всё работает).
- **Риск:** слабое железо даст медленные ответы. План: маленькая модель для демо плюс слайд про масштабирование на GPU-сервер.

### 10.2 Фотокнига: AI Auto-Create и AI Story Mode (трек 2)
Берём то, что у Mixbook называется Auto-Create и Story Mode, и делаем локально.

**Auto-Create (из набора фото в готовую книгу):**
1. Загрузка фото и чтение метаданных (время, геопозиция).
2. Фильтр: дубликаты, смазанные кадры, закрытые глаза, низкое разрешение.
3. Кластеризация по времени и смыслу в главы (поездка, день рождения и т.д.).
4. Выбор лучших кадров в каждой главе (оценка качества и разнообразия).
5. Раскладка по шаблонам: подбор макета под число и ориентацию фото, автокадрирование с учётом лиц.
6. Подписи к главам и страницам (генерация текста локальной моделью).
7. Редактирование: любой шаг можно отменить одним тапом.

**Story Mode (описал словами, получил книгу):**
- Пользователь пишет или говорит: «Книга про нашу поездку в Карелию, тёплый тон, 24 страницы, больше пейзажей».
- Локальная модель разбирает запрос в параметры: тема, тон, объём, акценты, обложка.
- Поиск подходящих фото по тексту (текстово-картиночные эмбеддинги), затем та же раскладка, что в Auto-Create.
- Диалог доработки: «убери фото с людьми на 5 странице», «сделай обложку из закатного кадра».

**Связь с остальными треками:** выбранный продукт, число страниц и время сборки пишутся в события, и дашборд показывает, сколько заказов фотокниг и где пользователи бросают сборку.

### 10.3 Что это даёт в позиционировании
- В фото-сегменте аналог Mixbook, но локально: фото клиентов не уходят третьим лицам.
- Единственная связка «умная сборка книги + аналитика производства + защищённый помощник».

### 10.4 Приоритеты внутри нового объёма
1. Обязательно: Auto-Create в упрощённой версии (фильтр, главы, раскладка по готовым шаблонам).
2. Обязательно: Story Mode как разбор запроса + поиск фото по тексту + сборка.
3. Если успеем: подписи, диалоговая доработка, голосовой ввод.
4. Только слайдом: обучение на предпочтениях клиента, 3D-превью книги.

### 10.5 Открытые вопросы
- Какое железо доступно на площадке и у команды (определяет размер моделей)?
- Разрешает ли «Фотопринт» тестовые фото или использовать только свои наборы?
- Какие форматы фотокниг и шаблоны есть у «Фотопринта» (Lite / Classic / Premium из App Store)? Раскладку нужно привязать к их реальным форматам.

## 11. Редизайн picPac (решение 08.11)
Делаем редизайн клиентского продукта под современный лад: **отдельно мобильное приложение и отдельно сайт**.

- **Бренд не меняем, а осовремениваем:** логотип, коралловый красный, тёплый бежевый остаются.
- **Стек:** мобильное приложение — React Native (Expo, демо с телефона через Expo Go); сайт — React (например, Next.js). Общие токены дизайна в одном файле `theme.ts`.
- **Процесс:**
  1. До 11.11: дизайн-система и кликабельные HTML-макеты ключевых экранов (мобильный и десктоп). Это дизайн, а не код приложения, поэтому безопасно при неясных правилах о заготовках.
  2. На хакатоне: перенос в React Native и React.
  3. Если нужно для питча: импорт HTML в Figma.
- **Правила HTML-макетов** (чтобы перенос в RN был механическим): токены в одном месте; только flexbox; экран из именованных компонентов (`PhotoGrid`, `ProductCard`, `QualityWarning`, `SpreadPreview`, `BottomBar`); явные состояния без hover (нажато, выбрано, загрузка, ошибка, пусто).
- **Объём:** редизайним только экраны демо-пути, остальное слайдами.
