# Use cases picPac One

Версия 2 (после аудита 07.11).

Приоритеты:
- **P0-демо** — входит в сквозной сценарий демо 12.11, режется последним;
- **P0** — обязательно, но вне основного сценария демо;
- **P1** — если успеем;
- **P2** — только слайдом.

Исполнители: В = Ваня, А = Алеся, М = Марк, И = Илья, С = Сеня.
Критерии успеха — **цели команды**, а не измерения. Базовые значения снимаем с текущего приложения.

## Команда и зоны ответственности
| Человек | Роль | Основная зона |
|---|---|---|
| Ваня | PM, FullStack | Сквозной сценарий, интеграция частей, питч, связка фронт-бэк |
| Алеся | Экономист, продуктовый аналитик | Метрики, правила отклонений, генератор данных, справочник продуктов, расчёт эффекта |
| Марк | LLM, Backend | Локальные модели, Auto-Create и Story Mode (AI-часть), модуль качества, ассистент, защита |
| Илья | Frontend | Интерфейсы: приложение и редактор, дашборд, чат ассистента |
| Сеня | Backend | API, БД (PostgreSQL), события, пайплайн данных, роли и журнал |

## Акторы
- **Клиент** — частный пользователь picPac.
- **Менеджер** — следит за заказами и производством.
- **Руководитель** — принимает решения, проводит встречи.
- **Администратор** — права, журнал, данные.
- **Система** — автоматические процессы (пайплайн, детекция).

Сотрудники цеха и поддержки не акторы, а источники данных (брак, чат «Обсудить»).

## Базовая линия: текущий путь заказа фотокниги
По скринам приложения: главная → «Фотокниги» → линейка (Classic) → параметры (формат, обложка, ламинация, развороты) → «Выбрать дизайн» → шаблон → редактор → **ручное заполнение каждой рамки через «+»** → «Заказать» → корзина → вход → доставка → оплата.
Задача: посчитать точное число тапов и время на тестовом наборе из 40 фото до начала разработки (В, А).

## Направление 1. Приложение picPac (клиентский путь, трек 2)

Ядро трека — **фотокнига** (самый длинный путь и выше чек). Фотопечать — дополнительный путь.

### UC-A1. Автосборка фотокниги (Auto-Create) — P0-демо
- **Актор:** клиент.
- **Предусловие:** выбран продукт и формат (например Classic 20×20), выбраны фото.
- **Сценарий:**
  1. Клиент нажимает «Собрать автоматически».
  2. Модуль качества (A8) отсеивает дубли, смазанные и низкого разрешения кадры.
  3. Система делит фото на главы по времени и содержанию.
  4. Выбирает лучшие кадры и раскладывает их по шаблонам разворотов с кадрированием (A8).
  5. Клиент видит готовую книгу и может править.
- **Альтернативы:**
  - фото мало для выбранного числа разворотов → предложить уменьшить книгу;
  - результат не нравится → переход в ручной редактор **без потери работы**;
  - любой шаг отменяется.
- **Критерий успеха:** из 40 фото готовая книга без пустых рамок; число тапов от выбора фото до заказа в разы меньше базовой линии.
- **Исполнители:** М (алгоритм и модели), С (хранение проекта), И (UI), В (интеграция).

### UC-A2. Сборка по описанию (Story Mode) — P0-демо
- **Актор:** клиент.
- **Сценарий:**
  1. Клиент пишет: «Книга про поездку в Карелию, тёплый тон, 24 страницы, больше пейзажей».
  2. Система разбирает запрос: тема, тон, объём, акценты.
  3. Подбирает шаблон по темам (love story, выпускной, день рождения, дети, путешествия и т.д.) и фото по тексту запроса.
  4. Собирает книгу по логике UC-A1.
  5. Клиент дорабатывает диалогом («убери людей на 5 странице»).
- **Ограничение:** текст клиента проходит модерацию (A15) и считается недоверенным (M5).
- **Критерий успеха:** запрос из одного предложения даёт книгу с заданным числом страниц и подходящей темой.
- **Исполнители:** М (разбор запроса, поиск фото), И (UI диалога), С (API), В (интеграция).

### UC-A8. Модуль качества и кадрирования — P0-демо (общий для A1 и A7)
- **Актор:** система.
- **Сценарий:**
  1. Проверка разрешения под выбранный формат (300 DPI; для печати 10×15 — 1205×1795 px, для разворота 20×20 — 4724×2398 px).
  2. Поиск лиц и главного объекта, кадрирование так, чтобы они не попали в зону риска и обреза (60 и 30 px на развороте, допуск печати).
  3. Поиск дублей и смазанных кадров.
  4. Понятные предупреждения клиенту: «Лицо у края — сдвинули кадр», «Мало пикселей для этого формата».
- **Критерий успеха:** на тестовом наборе ни одного лица в зоне обреза; предупреждение для каждого фото ниже порога.
- **Исполнители:** М (модели), И (отображение предупреждений), А (пороги по форматам).

### UC-A4. Оформление заказа — P0-демо
- **Актор:** клиент.
- **Сценарий:** «Заказать» → корзина → доставка (Европочта, Белпочта, EMS) → оплата (карта, ЕРИП) → статус заказа.
- **Результат:** заказ создан, события записаны в общий поток.
- **Исполнители:** С (заказы, статусы), И (экраны), В (интеграция).

### UC-A6. События клиентского пути — P0-демо (невидим для клиента)
- **Актор:** система.
- **Сценарий:** каждый шаг пишется как событие: выбор формата и шаблона, загрузка, автосборка, предупреждение качества (показано, принято, проигнорировано), заказ, отказ.
- **Результат:** данные для воронки и метрик брака на дашборде.
- **Исполнители:** С (схема событий), А (какие события нужны), И (отправка с клиента).

### UC-A14. Согласие на AI-обработку и удаление фото — P0
- **Актор:** клиент.
- **Сценарий:**
  1. Перед первой автосборкой клиент видит понятное согласие: фото обрабатываются внутри контура «Фотопринта», не передаются третьим лицам.
  2. После выполнения заказа фото удаляются через заданный срок; клиент может удалить их сам в любой момент.
- **Зачем:** персональные данные и лица на фото; это часть позиционирования «приватно».
- **Исполнители:** С (хранение и удаление), И (экран согласия), М (гарантия, что модели не сохраняют данные).

### UC-A3. Подбор продукта и формата — P1
- **Сценарий:** по числу и ориентации фото система предлагает линейку (Lite, Classic, Premium), формат и число разворотов с ценой и сроком из справочника (D14).
- **Исполнители:** А (правила и цены), С (API), И (UI).

### UC-A5. Повтор прошлого заказа — P1
- **Сценарий:** в «Заказах» кнопка «Повторить», подставляются продукт и дизайн из «Мои дизайны».
- **Исполнители:** С, И.

### UC-A7. Быстрая фотопечать — P1
- **Актор:** клиент.
- **Сценарий:**
  1. Главная → «Напечатать фото» → мультивыбор из галереи.
  2. По умолчанию 10×15, глянец, 1 шт., цена сразу.
  3. Автокадрирование и предупреждения через A8; подсказка «эта пропорция без обрезки ложится на 15×20».
  4. Массовая правка формата, бумаги и количества → заказ (A4).
- **Технология печати** (фотохимическая или цифровая) клиенту не навязывается: подсказывается или выбирается по умолчанию.
- **Исполнители:** И (2–3 экрана), М (через A8), С (через A4), А (правила формата).

### UC-A9. Загрузка из галереи — P1
- **Сценарий:** фоновая загрузка, работа при плохой сети, продолжение после обрыва.
- **Исполнители:** С, И.

### UC-A10. Отложенный вход — P1
- **Сценарий:** собрать книгу без регистрации; вход по телефону только при оплате, черновик привязывается к аккаунту.
- **Исполнители:** С, И.

### UC-A11. Брошенная сборка — P1
- **Сценарий:** автосохранение черновика и напоминание вернуться к незаконченной книге.
- **Исполнители:** С, И, А (когда и как напоминать).

### UC-A12. Статус заказа и уведомления — P1
- **Сценарий:** уведомления о смене этапа (принят, в печати, в пути) и трек-номер.
- **Исполнители:** С, И.

### UC-A13. Претензия по браку — P1
- **Актор:** клиент.
- **Сценарий (трёхступенчатая схема):**
  1. Клиент фотографирует дефект в приложении, выбирает заказ.
  2. AI проверяет фото на типовые признаки брака (полосы, смещение, обрезка, цвет).
  3. Очевидный брак → **переделка без возврата** изделия.
  4. Если нужен возврат → бесплатный возврат через пункты Европочты.
- **Данные:** претензия привязана к заказу, линии и смене и попадает в метрики брака (D2, D3).
- **Этап 2 (слайд):** партнёрские постаматы для возврата и выдачи заказов.
- **Открытые задачи Алеси:** расчёт «переделка против возврата»; есть ли у Европочты постаматы и возвратные ярлыки.
- **Исполнители:** М (проверка фото), С (претензии и связи), И (экран), А (экономика).

### UC-A15. Модерация контента — P1
- **Сценарий:** проверка фото и текстов подписей Story Mode на запрещённый контент до печати; спорное уходит на ручную проверку.
- **Исполнители:** М, С.

## Направление 2. Данные и дашборд picPac Insight (трек 1)

### UC-D0. Генерация тестовых данных с заложенными историями — P0-демо
- **Актор:** команда.
- **Сценарий:** генератор создаёт данные за несколько месяцев: клиенты, заказы, события приложения, финансы, производство, кадры, претензии.
- **Структура производства** (реконструкция по сайту, подтвердить на лекции 1): фотохимическая печать (Fuji Frontier), цифровая печать и Lite/Classic (Ricoh), Premium (Noritsu).
- **Сезонность:** выпускные, Новый год, свадебный сезон.
- **Заложенные истории для демо:**
  - всплеск брака на одной линии в определённые смены;
  - падение маржи из-за глубоких скидок (на сайте до 30%, на скрине заказа скидка около 35%);
  - рост отказов в приложении после изменения шага заказа;
  - задержки из-за нехватки сотрудников.
- **Исполнители:** А (бизнес-логика и истории), С (реализация и загрузка).

### UC-D1. Приём и очистка данных — P0-демо
- **Актор:** система, администратор.
- **Сценарий:**
  1. Загрузка данных из генератора или файлов.
  2. Проверки: схема, пропуски, дубли, выбросы, связность (заказ без клиента).
  3. Результат проверок виден на странице качества данных.
- **Исполнители:** С (пайплайн), А (набор проверок), И (страница).

### UC-D2. Просмотр KPI — P0-демо
- **Актор:** менеджер, руководитель.
- **Сценарий:** ключевые показатели по финансам, клиентам, производству и кадрам с динамикой за период.
- **Исполнители:** А (метрики и формулы), С (витрины), И (дашборд).

### UC-D3. От агрегата к причине (drill-down) — P0-демо
- **Актор:** менеджер, руководитель.
- **Сценарий:**
  1. На дашборде виден скачок показателя (например, рост брака).
  2. Клик → раскладка по измерениям: продукт, линия, смена, сотрудник, поставщик, время.
  3. Система выделяет измерение, сильнее всего объясняющее отклонение, и пишет текст причины с цифрами.
- **Метод:** правила, пороги и вклад измерений; числа считает код, не LLM.
- **Критерий успеха:** на каждой заложенной истории D0 система находит правильную причину.
- **Исполнители:** А (методика, пороги), С (расчёт), И (интерфейс).

### UC-D4. Автодетекция отклонения — P0-демо
- **Актор:** система.
- **Сценарий:** метрика выходит за порог или статистическую норму → создаётся карточка отклонения с привязкой к данным.
- **Исполнители:** А (правила), С (расчёт и хранение).

### UC-D5. Оформление решения по отклонению — P0-демо
- **Актор:** руководитель.
- **Сценарий:** в карточке: причина (подтверждена или изменена), решение, ответственный, срок. Статусы: открыто, в работе, на проверке эффекта, закрыто.
- **Исполнители:** С (модель и API), И (карточка), А (поля и статусы).

### UC-D8. Проверка эффекта решения — P0-демо
- **Актор:** система.
- **Сценарий:** после выполнения решения система следит за метрикой заданный период. Вернулась в норму → отклонение закрывается с отметкой эффекта. Не вернулась → карточка снова открыта.
- **Зачем:** цикл замыкается по данным, а не по галочке.
- **Исполнители:** А (правило оценки эффекта), С (расчёт), И (отображение).

### UC-D11. Ролевой доступ к дашборду — P0
- **Сценарий:** роли видят только свои данные; кадровые и зарплатные показатели — только руководителю и администратору. Те же права действуют на ассистента (M5).
- **Исполнители:** С (роли), А (какие данные чувствительны), И.

### UC-D6. Воронка клиентского пути — P1
- **Сценарий:** воронка от выбора формата до заказа с долей отказов по шагам и сегментам.
- **Исполнители:** А, С, И.

### UC-D9. Уведомление ответственного — P1
- **Сценарий:** при создании отклонения ответственный за область получает уведомление со ссылкой на карточку.
- **Исполнители:** С.

### UC-D10. Ложные отклонения и сезонность — P1
- **Сценарий:** пользователь помечает отклонение как ложное или сезонное; пороги учитывают сезонность (выпускные, праздники).
- **Исполнители:** А, С.

### UC-D12. Юнит-экономика заказа — P1
- **Сценарий:** маржа заказа с учётом себестоимости, скидки, промокода и доставки; срез по продукту и каналу.
- **Исполнители:** А (модель), С, И.

### UC-D14. Единый справочник продуктов и условий — P1
- **Сценарий:** форматы, цены, сроки, допуски, условия возврата хранятся в одном месте; сайт, приложение и ассистент берут данные оттуда.
- **Зачем:** на picpac.by найдено 11 противоречий (сроки, допуски, единицы объёма книги, формат 30×45 без цены, условия брака и др., таблица в notes/06). Показываем в презентации.
- **Исполнители:** А (наполнение), С (хранение и API).

### UC-D7. Прогноз и «что если» — P2
- Слайд: прогноз загрузки линий и выручки.

### UC-D13. Подключение реального источника — P2
- Слайд: CSV, 1С, API «Фотопринта». Аргумент пути к промышленному развитию.

## Направление 3. AI-помощник picPac Ассистент (трек 3)

### UC-M1. Вопрос о бизнесе на естественном языке — P0-демо
- **Актор:** руководитель.
- **Сценарий:**
  1. Вопрос: «Почему упала маржа на фотокнигах?»
  2. Помощник вызывает инструменты запросов к витринам с правами пользователя.
  3. Числа считает код, вывод формулирует локальная модель.
  4. В ответе ссылки на источники (витрина, документ).
- **Если данных не хватает:** помощник говорит «не знаю» и показывает, чего не хватает, а не выдумывает.
- **Критерий успеха:** на заложенных историях D0 ответ называет правильную причину, все числа совпадают с витринами.
- **Исполнители:** М (оркестратор, инструменты, промпты), С (витрины и права), И (чат), А (проверка выводов).

### UC-M2. Подготовка встречи по отклонениям — P0-демо
- **Актор:** руководитель.
- **Сценарий:** повестка из открытых отклонений и невыполненных задач, контекст и вопросы к участникам.
- **Исполнители:** М, С, И.

### UC-M3. Протокол и итоги встречи — P0-демо
- **Актор:** руководитель, помощник.
- **Сценарий:**
  1. Загружается запись или текст встречи (локальное распознавание речи для аудио).
  2. Помощник формирует протокол, решения и поручения с ответственными и сроками.
  3. **Руководитель подтверждает** решения и задачи перед созданием; помощник только предлагает.
  4. Подтверждённые решения создают карточки и задачи, связанные с отклонениями (D5).
- **Исполнители:** М (распознавание, извлечение решений), С (задачи и связи), И (экран итогов), В (интеграция цикла).

### UC-M5. Защита и журнал — P0-демо
- **Актор:** администратор.
- **Сценарий:**
  1. Права пользователя ограничивают данные и документы, доступные помощнику (те же, что D11).
  2. Персональные данные маскируются до модели и журнала.
  3. Недоверенным считается любой внешний текст: документы **и клиентские тексты** (запросы Story Mode, комментарии к заказам, чат «Обсудить»). Инструкции внутри них не выполняются.
  4. Инструменты помощника только на чтение и только по разрешённым витринам; запись (задачи, решения) только через подтверждение человеком.
  5. Журнал: кто спросил, какие данные использованы, что ответила модель.
  6. Все модели работают в локальном контуре.
- **Критерий успеха:** демо-атака инструкцией в комментарии к заказу не срабатывает; пользователь без прав не получает кадровых данных через помощника.
- **Исполнители:** М (маскирование, защита), С (роли, журнал), И (экран журнала), А (чувствительные поля).

### UC-M4. Поиск по корпоративным документам — P1
- **Сценарий:** вопрос по регламенту или договору → ответ с цитатой и ссылкой, только по доступным пользователю документам.
- **Исполнители:** М (поиск, локальные эмбеддинги), С (хранилище и права).

### UC-M6. Контроль задач — P1
- **Сценарий:** напоминания о просроченных задачах, синхронизация статуса с карточкой отклонения.
- **Исполнители:** С, М.

### UC-M7. Управленческие итоги за период — P1
- **Сценарий:** отчёт за неделю: принятые решения, их эффект (D8), просрочки, открытые отклонения.
- **Исполнители:** М, С, А.

### UC-M8. Документ по решению — P1
- **Сценарий:** черновик служебной записки или приказа по шаблону на основе решения; человек правит и утверждает.
- **Исполнители:** М, И.

### UC-M10. Поиск противоречий в документах — P1
- **Сценарий:** помощник сравнивает документы и материалы (сайт, регламенты, справочник D14) и находит расхождения: разные сроки, допуски, условия.
- **Демо:** реальные 11 противоречий с picpac.by.
- **Исполнители:** М, А.

## Нефункциональные требования
- **Локальный контур:** все модели и данные внутри периметра; в демо показать работу без интернета.
- **Устойчивость демо:** если локальная модель тормозит, есть заранее посчитанный результат для каждого шага сценария.
- **Производительность:** целевое время ответа помощника и автосборки книги задаём после выбора железа и моделей.
