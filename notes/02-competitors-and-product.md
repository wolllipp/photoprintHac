# Продукт на выходе и сравнение с аналогами

Статус данных: по аналогам собрано поверхностно (вендорские сравнения, часть без независимой проверки). Всё помеченное «?» нужно проверить руками до питча.

## 1. Как выглядит продукт на выходе
Три экрана одной истории:

1. **Мобильное приложение (клиент).** Открыл -> выбрал фото -> система предложила продукт и макет -> подтвердил -> заказ. Цель: минимум шагов, видимый счётчик «заказ за N секунд».
2. **Командный дашборд (менеджер).** KPI по финансам/клиентам/производству/кадрам. Клик по отклонению -> цепочка причин -> карточка решения (причина, ответственный, срок, статус).
3. **AI-помощник (руководитель).** Чат + режим встречи: повестка из актуальных отклонений, протокол, задачи. Каждый ответ со ссылкой на источник. Журнал действий.

## 3. Чем мы отличаемся (честно)
Отдельно ни одно из трёх направлений мы не сделаем лучше Mixbook, Power BI или Copilot за полтора дня. Наше преимущество только в **связке**:

1. **Замкнутый цикл.** Заказ клиента -> метрика -> отклонение -> причина -> встреча -> решение -> задача -> возврат в метрику. У аналогов цикл разорван между разными продуктами.
2. **Помощник знает цифры компании.** Повестка встречи строится из реальных отклонений, а не из календаря. Универсальные помощники этого не делают.
3. **Защита как часть продукта.** Права пользователя действуют на ответы помощника, ПДн маскируются до модели, каждый ответ с источником и журналом. Это прямо в формулировке трека 3.
4. **Домен фотопечати.** Приложение, дашборд и помощник говорят одним языком: продукт, заказ, смена, брак, срок.
5. **Данные из приложения идут в аналитику.** Видно, где клиенты бросают заказ, и это становится метрикой на дашборде.

## 4. Чего не стоит обещать
- Что мы «лучше Mixbook» в раскладке фотокниг или «лучше Power BI» в визуализации.
- Точности AI-ответов без показа источников.
- Интеграции с реальными системами «Фотопринта» (до лекции 1 мы их не знаем).
