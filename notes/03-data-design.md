# Как работают данные (черновик для обсуждения)

Статус: идея и выбор подхода, код не пишем. Пункты с пометкой «ВЫБОР» требуют решения команды, рядом дана рекомендация.

## 1. Принципы
1. **Один источник правды.** Приложение, дашборд и AI читают одни и те же данные, а не копии.
2. **Всё локально.** Данные и модели внутри периметра (решение из раздела 10 концепции).
3. **Событие первично.** Всё, что происходит (шаг в приложении, смена статуса заказа, брак, решение), пишется как событие. Метрики считаются из событий.
4. **AI не ходит в сырые таблицы.** Помощник работает через ограниченные «витрины» и инструменты с проверкой прав.
5. **Данные тестовые и обезличенные.** Генерируем сами, а реальные от «Фотопринта» подключаем, если дадут.

## 2. Потоки данных
```
Приложение (события, заказы, фото)
        |
        v
 [Приём] -> [Очистка и проверки качества] -> [Единая модель]
                                                   |
                    +------------------------------+-----------------+
                    v                              v                 v
              Витрины/метрики              Хранилище фото      Документы и
              (для дашборда)               + эмбеддинги        протоколы встреч
                    |                              |                 |
                    +------------- AI-слой (локальный) -------------+
                                        |
                          Решения, задачи -> обратно в единую модель
```

## 3. Источники данных
| Область | Что содержит | Откуда в прототипе |
|---|---|---|
| Клиенты и заказы | клиент, заказ, позиции, статус, канал, доставка | приложение + генератор |
| События приложения | открытие, выбор фото, этапы сборки, отказ | приложение |
| Финансы | выручка, себестоимость, маржа, оплаты | генератор |
| Производство | смены, станки/цеха, брак, сроки, простои | генератор |
| Кадры | сотрудники, смены, загрузка, отсутствия | генератор |
| Решения и задачи | отклонение, причина, ответственный, срок, статус | создаются в системе |
| Документы | регламенты, протоколы, договоры | сгенерированные тексты |
| Фото | загруженные пользователем + эмбеддинги | тестовые наборы |

## 4. Единая модель (ядро)
Ключевые сущности и связи:
- Клиент -> Заказ -> Позиция заказа -> Продукт
- Заказ -> Производственная операция -> Смена -> Сотрудник
- Заказ -> Платёж / Финансовая проводка
- Отклонение -> Причина -> Решение -> Задача -> Ответственный
- Встреча -> Протокол -> Решения/Задачи
- Фотокнига (проект) -> Страницы -> Фото

Именно связь «заказ -> операция -> смена -> сотрудник» даёт путь от агрегата к причине.

## 5. Как работает «от агрегата к причине»
1. Метрика (например, доля брака) выходит за порог или по статистике отклоняется от нормы.
2. Система автоматически создаёт **отклонение**.
3. Раскладка по измерениям: продукт, цех, смена, сотрудник, поставщик материала, время. Выбирается измерение, которое сильнее всего объясняет изменение.
4. Результат: текст причины («брак в цехе 2 в ночные смены вырос на 40%, совпало с простоем станка»), цифры и ссылки на данные.
5. Руководитель принимает решение, оно записывается как объект и привязывается к отклонению.

ВЫБОР (метод поиска причин):
- A. Правила и пороги плюс вклад измерений (простой, объяснимый). **Рекомендую для прототипа.**
- B. Статистические модели аномалий. Можно добавить позже.
- C. Только LLM по таблицам. Не рекомендую: возможны ошибки в цифрах, цифры должны считаться кодом, а LLM только объясняет.

## 6. Роль AI в данных
- **Считает код, объясняет модель.** Числа берутся запросами к витринам, LLM формулирует вывод.
- **Инструменты помощника:** запрос к витрине метрик, поиск по документам, чтение протоколов, создание задачи. Каждый вызов проверяет права.
- **Источники:** в ответе указывается, из какой витрины и какого документа взят факт.
- **Журнал:** кто спросил, какие данные использованы, что ответила модель.

## 7. Данные фотокниги
- Фото хранятся локально, для каждого считаются: метаданные, качество, лица (без идентификации личности), эмбеддинг для поиска по тексту.
- Проект книги хранит: выбранные фото, главы, макеты, подписи, историю правок.
- Доступ к фото только у владельца, AI-слой видит их только в контексте его сессии.

## 8. Безопасность и права
- Роли: клиент, менеджер, руководитель, администратор.
- Помощник работает с правами конкретного пользователя.
- Персональные данные маскируются до попадания в промпт и в журнал.
- Документы считаются недоверенными: защита от инструкций внутри текста (prompt injection).

## 9. Качество данных
Проверки при приёме: схема, пропуски, дубли, выбросы, согласованность связей (заказ без клиента, смена без сотрудника). Результат проверок виден на отдельной странице, это часть демо трека 1.

## 10. Тестовые данные
Генератор создаёт правдоподобные данные за несколько месяцев с сезонностью (праздники, выпускные) и **заложенными историями**:
- всплеск брака в одном цеху в определённые смены;
- рост отказов в приложении после изменения шага заказа;
- задержки из-за нехватки сотрудников.

Эти истории и есть сценарии демо.

## 11. Выбор технологий (ВЫБОР, рекомендации)
| Задача | Рекомендация | Альтернатива |
|---|---|---|
| Операционная БД и витрины | PostgreSQL | SQLite (проще, но слабее для демонстрации масштаба) |
| События | таблица событий в PostgreSQL | очередь (Kafka/Redis), только слайдом |
| Хранилище файлов | локальная папка / MinIO | |
| Векторный поиск | pgvector в той же БД | отдельная векторная БД |
| Локальные LLM | Ollama | vLLM, если будет GPU |
| Аналитика/дашборд | свой веб-интерфейс на данных витрин | Metabase/Superset как быстрый старт |

Рекомендация: **один PostgreSQL** на всё (операции, события, витрины, векторы). Меньше компонентов, проще объяснить архитектуру.

## 12. Открытые вопросы

2. Хранить ли фото клиентов в демо долго или удалять после сборки (важно для рассказа про приватность)?
3. Дашборд делаем своим интерфейсом или на готовом инструменте (Metabase/Superset)? Свой красивее для демо, готовый быстрее.
4. Метод поиска причин: подходит вариант A?
5. Что считаем главным демо-сценарием: брак в производстве или падение конверсии в приложении?
